## 摘要

本作品面向信号处理与电路实验教学，在PYNQ-Z2上建立从模拟音频输入、PL定点信号处理到PS分析和浏览器显示的完整链路。PL承担I2S接收、1024点分帧、矩形或Hann加窗、流水FFT及AXI-Stream帧控制；PS解析硬件复数结果、恢复尺度并完成峰值分析、记录和可视化，主线不重复执行软件FFT。同步双声道时域采集支持被测系统的幅频与相频测量。

12个主案例及2个恢复帧的RTL输出与官方定点模型逐点一致；r2完成1820.013秒、9100帧长测，r3完成短复验和三次实际冷启动。历史RC低通实验含16点、96块，拟合截止1547.7446 Hz，较元件理论值偏差+0.4343%。r4形成当前频谱、深入分析、我的记录、演示样例和频率响应测量五个功能界面，后者支持RC低通与通用系统两类测量。本文展示本版实际界面与用户保存结果；10项集成及72项扩展主机测试另有记录，界面截图的证据范围不扩写为完整r4交互验收。

## 1 选题背景与FPGA系统价值

### 1.1 实际问题与已有基础

音频与基础电路实验既需要看到频谱和幅相曲线，也需要解释信号经过接口、定点运算和数据搬运后为何得到这些结果。本作品把采样、算法、协议状态和原始留样关联起来，使学生能够从波形追查到硬件与数值契约，而不只观察一张曲线。

已有pynq-audio开源项目提供ADAU1761配置、I2S接口及音频DSP示例。本作品沿用其MIT许可I2S和codec基础，自主完成本项目的分帧控制、窗与缩放契约、复数封装、状态检查、PS服务和证据归档；不把第三方接口代码或AMD FFT IP宣称为自研内核。[2]

| 方案 | 适用优势 | 本作品选择依据 |
| --- | --- | --- |
| PC声卡与软件FFT | 开发快速，算法灵活 | 可计算频谱，但无法替代本工程已实现的PL状态机和接口实验对象 |
| ARM侧纯软件FFT | 便于算法迭代 | 可作为计算基线；采集边界和硬件握手仍需专门链路 |
| PL采集和FFT配合PS | 接口控制、定点运算、搬运可明确分层 | 让采样协议、数值和应用在同一Zynq平台形成可验证闭环 |

### 1.2 本方案中不能直接省去的PL职责

PL直接连接codec的I2S信号，以时钟驱动的硬件逻辑组织左右样本、帧触发和1024点边界。Linux/Python仅下发控制并处理完成后的数据，不承担逐拍I2S接收。若直接删除PL，这条板载codec到DDR的数据路径就会断开，必须另行设计采集接口或更换硬件。

PL流水FFT把量化、窗乘法和变换固定在可逐整数验证的数据通路中；AXI valid/ready、TLAST以及ABORT恢复由状态机处理。其价值是可控接口、可解释定点运算与可扩展数据通路。PS保留交互、拟合与记录的灵活性，避免为界面和非固定算法付出硬件开发成本。

这种必要性针对本作品的硬件架构，并不表示频谱或RC算法只能由FPGA完成。当前约5帧/秒来自应用快照调度，尚无同口径PL加速比、功耗收益或端到端确定性延迟数据。

## 2 系统原理与软硬件划分

图1 系统数据通路与控制关系

普通频谱链路为电脑模拟输出→LINE IN→ADAU1761→I2S→PL窗和FFT→64位复数打包→S2MM DMA→DDR→PS分析→浏览器。PS通过I2C配置codec，通过AXI-Lite选择窗口、触发采集并读取状态。

| 层级 | 实际承担的功能 | 划分依据 |
| --- | --- | --- |
| PL | I2S接收、分帧、定点加窗、1024点FFT、TLAST和错误状态 | 逐拍接口与固定数值通路适合时钟驱动硬件实现 |
| PS | 尺度恢复、单边幅值、局部峰、相量拟合、模式协调、记录 | 算法和交互经常变化，软件实现便于迭代与复核 |
| 浏览器 | 频谱、瀑布、游标、回放和用户操作 | 显示与硬件访问解耦，界面操作不直接驱动DMA |

主线FFT固定处理左声道，允许双声道音频输入，但不混合左右、不提供双路同时频谱。双音素材的每个声道都包含1 kHz与3 kHz；不能把左1 kHz、右3 kHz输入解释为主线的两个频谱峰。

频率响应使用另一套M4 Overlay采集同步双声道时域块，左为输入参考、右为被测系统输出。r4通过同进程互斥协调FFT与M4两套Overlay，支持RC低通和通用系统的幅相测量；这不等于主线具有双路FFT相位测量。

## 3 RTL接口与定点数值设计

### 3.1 帧控制和协议完整性

每次START组织一帧1024点，帧之间允许间隙。控制模块维护配置完成、忙、输入/输出计数、帧序号和错误事件；忙时重复START不排队，ABORT后按既定清理和重新配置流程恢复。AXI4-Stream背压时数据与TLAST保持，最后一拍标识帧尾。

| 接口 | 定义 | 核对方式 |
| --- | --- | --- |
| 输入 | signed24左声道，算术右移8位形成signed16 | 输入与量化窗口级逐点参考 |
| 窗口 | 矩形或对称Hann，Q1.15系数，乘积右移15位 | 冻结系数哈希与实际RTL输入捕获 |
| FFT IP | xfft 9.1，pipelined_streaming_io，固定1024点，自然序 | 17项配置读回与官方定点模型 |
| 复数输出 | uint64低32位real、高32位imag，signed16分别符号扩展 | 1024拍，8192 B，状态和长度联合检查 |
| 控制 | START、ABORT、CLEAR、WINDOW和状态寄存器 | AXI-Lite与恢复/背压协议仿真 |

### 3.2 幅值尺度只恢复一次

前向FFT配置字0x0557，总缩放S=11。输出整数yr、yi恢复为X[k]=(yr+j·yi)×2¹¹/32768，即实部和虚部分别除16。单边幅值为|X[k]|除以实际窗系数和，中间正频点乘2，DC和Nyquist不乘2。

矩形窗系数和为1024，Hann为511.50006103515625。dBFS以峰值满量程为基准；绘图零值下限只是数值显示处理，不代表实测模拟噪声底。频轴使用本次实测采样率，不把100 MHz PL时钟误作音频采样率。

### 3.3 对初级组设计能力的体现

本作品的RTL工作覆盖串行接口、帧缓存和状态机、AXI-Lite控制、AXI4-Stream流控及定点数据解释。功能正确性同时要求数值、长度、结束标记和异常恢复成立，单独一条频谱曲线无法替代这些检查。

使用流程为“当前频谱观察→深入分析截取→保存到我的记录→选择留样进一步分析”。用户记录位于软件目录外的../user_data/records，与内置演示样例分开保存，并用SHA256校验。完整频谱为有限、稀疏留样，不是连续音频；回放不插补缺失频谱，缩放和游标不提高1024点FFT的实际频率分辨率。

## 8 同步双声道与RC扩展实验

RC使用M4_RAW_STEREO同步块，形状(2,1024)，signed24样本存为int32。左声道为输入参考，右声道为RC输出；对两通道用共同频率分别拟合正弦、余弦及DC项，得到复相量Cy/Cx，再除以直通响应C0(f)。这条相位链路与主线单路FFT分开。

x[n] = a cos(2πfn/fs) + b sin(2πfn/fs) + c
H_cal(f) = (Cy / Cx) / C0(f)
H_RC(f) = 1 / (1 + j2πfRC)

## 11 ROSS参与开发的具体方式

项目把ROSS作为研发辅助工具链使用：开发者提出约束，AI客户端读取AMD Agent Skills，借助Vivado MCP执行Tcl并读取实际日志；AMD文档检索提供IP与工具依据。ROSS不属于上板运行依赖，也不参与最终频谱数值计算。[3]

| 环节 | 本项目可核对的材料 | 实际作用 |
| --- | --- | --- |
| 工具接入 | 2026-10-23安装验证记录；原生日志中的ross_init与MCP命令标记 | 使AI能读取和操作真实Vivado上下文，避免只生成未经执行的脚本 |
| FFT集成 | 17项FFT配置读回、原生BD导出和连线重建对比 | 固定点数、格式、缩放、顺序、时钟与DMA宽度 |

| 失败纠正 | GP0只读参数失败日志、agent.log、rebuild_comparison.json | 保留失败，转向核对实际接口时钟与连接关系 |
| 软件与交付 | r3导出修复说明、CMA复核和本次提交审计 | 限定修改范围，区分测试层级与版本归属 |

### 11.1 通过真实反馈修正判断

集成时曾尝试把PS参数PCW_M_AXI_GP0_FREQMHZ从10改为100，Vivado返回该属性只读。后续没有把未生效的写入记为成功，也没有为消除注释而调整DDR或PLL；而是检查实际FCLK和AXI接口均为100000000 Hz，并保留原参数对比与失败审计。

原生BD重建记录显示组件名、标量与接口连接一致，17项FFT属性通过比对。重建中该注释解析为100 MHz，但这只证明BD重建范围，不是第二次综合，也不保证bitstream逐字相同。该案例体现了从“尝试修改”到“接受工具约束并缩小结论”的纠错过程。

### 11.2 人与智能体的职责

团队负责选题判断、接线、供电、音频播放、实板执行和最终结果确认；AI辅助形成代码、检查接口、分析日志和整理材料。没有证据支撑的计量指标保持空缺，AI生成的文字不能替代实测输出。

## 13 技能包的提炼过程与边界

### 13.1 PYNQ Overlay与DMA调试技能

路径为skill/pynq_overlay_dma_bringup。经验来自接口宽度不匹配、硬件线程缺少事件循环、端口被旧服务占用、MCLK与实际时钟注释不一致，以及只看DMA done不足以判定帧正确等观察。技能将这些问题整理为身份校验→MMIO→长度和流控→原始样本→黄金参考的逐层检查。

使用时先读skill.md和检查表，把器件、Overlay路径、寄存器、DMA方向和数据宽度替换为目标工程参数。检查脚本只做其声明的静态能力；真实MMIO/DMA及板测仍须按目标平台执行。基础r3的三次冷启动和当前项目的M4验证是项目内效果，不是跨板卡验证。

迁移到别的PYNQ题目时，身份、接口、缓冲生命周期和证据分层方法可复用；PS DDR、HP端口、codec和时钟必须重新确认。双进程争用硬件、bit/hwh不匹配、无法确认安全停止时，不能按成功路径继续加载另一个Overlay。

### 13.2 FPGA交付审计技能

路径为skill/fpga_delivery_audit。它来自旧ZIP未更新、目录大小写造成跨平台差异、源码与清单不一致，以及把主机通过误记为整板验收等问题。使用方法是指定工程根目录，检查必需目录、文件名、哈希覆盖、资产非空和验收字段。

本轮对收件实施独立CRC、路径安全和SHA256覆盖检查，发现原包校验清单完整，但清单完整并不保证必需工程内容齐全；随后按指南逐项发现BD、原始报告及测试平台的缺失。这一观察被补入技能，要求区分“字节未损坏”和“内容满足复现”。

## 14 从零复现所需环境与主机步骤

工程根为pynq_z2_spectrum_analyzer。src含RTL、约束和PS源码镜像，sim含历史向量与验证结果，build含正式复现入口与实现报告，board含冻结Overlay和运行包，data含实测原件，skill含经验包，report含设计与协作记录。所有命令从包根执行。

### 14.1 环境与文件身份

硬件构建需Vivado 2026.1、xc7z020器件支持、PYNQ-Z2 board files和适用IP许可；主机分析需Python与NumPy，JavaScript检查需Node.js。板端历史环境为PYNQ3.1.1、Python3.10.4、NumPy1.21.5和Linux6.6.10。不同平台版本应记录，不直接继承既有验收结论。

python build/scripts/verify_package.py
python board/scripts/check_assets.py

上述命令检查提交文件。软件回归入口为build/scripts/run_host_tests.py，既有10项集成及72项扩展主机测试保留独立结果记录。board/software中的ZIP是板端运行来源，src/ps/pynq_r4是小写化阅读镜像；二者用途不同，部署使用原运行包。

### 14.2 硬件构建与RTL复现入口

vivado -mode batch -source build/scripts/rebuild_fft.tcl
  -tclargs D:/fft_rebuild_new

上面的换行用于排版，实际执行写成一行。输出目录必须不存在；构建脚本添加RTL/XDC，调用原生BD导出并生成wrapper，再综合、实现和生成报告，既有bit/hwh不被覆盖。2026-11-04已在本机独立解压副本完成FFT BD/wrapper生成、仿真编译展开及FFT/M4综合实现。原始日志和新报告见build/reports/clean_build_20261104；不重复数值矩阵，不新增板测。

python src/reference/fft_chain/verify_fft_chain.py prepare
  --out D:/fft_results_new
vivado -mode batch -source build/scripts/run_fft_chain.tcl
  -tclargs D:/fft_sim_new D:/fft_results_new
python src/reference/fft_chain/verify_fft_chain.py verify
  --out D:/fft_results_new

每条命令分别合并为一行。M4测试平台入口为build/scripts/sim_m4.tcl，构建入口为build/scripts/build_m4_from_sources.tcl。冻结参考来自官方定点模型；重新生成模型输出需要同版Vivado安装内的模型库。已保存的历史参考与新执行输出分别标记来源。
